# 五容器验收环境 Mock 方案

## 目标

这份文档用于回答两个问题：

1. 能不能在本机 macOS 上先模拟“5 个验收容器”的部署环境？
2. 能不能像验收时那样，分别用多个终端连接这些容器做监控，同时用一个控制面终端执行演示命令？

结论先说：

- 可以在 macOS 上用 Docker Desktop 模拟出 5 个 Linux 容器。
- 可以把容器名固定成 `t9-ct1` 到 `t9-ct5`。
- 可以把容器内部 IP 固定成 `10.10.9.1` 到 `10.10.9.5`。
- 可以在容器里启动多个 `ddb-server` 进程，所以不需要把架构改成“3 个 group，每组 5 节点”。
- 可以用 5 个终端分别连进这 5 个容器做监控。
- 但这只是“高保真 mock”，不是和验收环境 100% 等价的网络环境。

## 这套 mock 能解决什么问题

这套本地模拟的核心价值，不是复刻远程登录入口本身，而是提前暴露部署问题：

- `etcd_host` 是否填写正确
- `default_join_host` 是否填写正确
- `join` 顺序是否正确
- 端口是否冲突
- 一个容器内跑多个 shard 进程时，数据目录和日志目录是否隔离
- `inspect`、`move-shard`、故障演示是否还能正常工作
- 9 个 shard 节点分布到 5 个容器后，副本是否仍然被正确打散

## 能否在 mac 上完整模拟 5 个容器

可以，但需要理解一个边界：

- 容器之间通过自定义 Docker 网络通信，这一点和真实 Linux 容器非常接近
- 容器可以拥有固定内网地址，例如 `10.10.9.1` 到 `10.10.9.5`
- 但是你宿主机 macOS 对 Docker 内部网络的访问方式，和真实 Linux 宿主机并不完全一样

所以更准确的说法是：

- 它可以高保真模拟“5 个节点之间如何互相通信”
- 可以高保真模拟“控制平面、shard、join、Raft、inspect、迁移”
- 但不能 100% 复刻“学校验收机房里的 SSH 跳板行为”

对于当前目标，这已经足够。

## 推荐架构：保持 3 个 group，每组 3 副本

不建议改成：

- 3 个副本组
- 每组 5 个节点

原因：

- 这会把 shard 进程总数从 9 个增加到 15 个
- 端口、日志、数据目录、Raft 复制流量都会明显变复杂
- 课程展示不需要 5 副本才能说明容灾与复制
- 3 副本已经足够表达 Raft 多数派和组内复制

建议保持现有设计：

- `g1`、`g2`、`g3` 三个 shard group
- 每组 3 副本
- 共 9 个 shard 进程

## 一个容器能否运行多个进程

可以。

当前项目本来就是“单机 / 单宿主机上启动多个 shard 进程”的设计思路：

- 一份机器配置里可以包含多个 `targets`
- 每个 `target` 会起一个独立的 `ddb-server`
- 各进程之间通过不同的 `http_port`、`raft_port`、数据目录和日志目录隔离

因此，从系统语义上说：

- 一个容器就等价于一台“轻量 Linux 主机”
- 在一个容器里启动 2 到 3 个 shard 进程是完全可行的

## 推荐的五容器进程分布

建议把 5 个容器按下面方式使用：

- `t9-ct1 (10.10.9.1)`：控制平面
- `t9-ct2 (10.10.9.2)`：部分 shard
- `t9-ct3 (10.10.9.3)`：部分 shard
- `t9-ct4 (10.10.9.4)`：部分 shard
- `t9-ct5 (10.10.9.5)`：部分 shard

推荐进程分布如下：

- `t9-ct1`
  - `etcd`
  - `apiserver`
- `t9-ct2`
  - `g1-n1`
  - `g2-n2`
- `t9-ct3`
  - `g1-n2`
  - `g3-n1`
- `t9-ct4`
  - `g1-n3`
  - `g2-n1`
  - `g3-n2`
- `t9-ct5`
  - `g2-n3`
  - `g3-n3`

这样分布的好处是：

- 同一个 group 的 3 个副本不会落在同一个容器里
- 仍然保持“分片 + 组内复制”的演示语义
- 5 个容器全部都用上了
- 不需要修改系统核心设计

## 为什么这个分布是合理的

按上面的分布：

- `g1` 分布在 `ct2`、`ct3`、`ct4`
- `g2` 分布在 `ct2`、`ct4`、`ct5`
- `g3` 分布在 `ct3`、`ct4`、`ct5`

这意味着：

- 任何一个副本组都没有把 3 个副本压在同一个容器里
- 单个容器故障不会直接导致一个 group 的全部副本都消失
- 虽然 `ct4` 比较重，但它不会破坏副本打散原则

如果后续要更均衡，也可以把某些节点重新分配，但第一版 mock 方案没必要追求绝对均匀。

## 控制平面如何放

当前项目的控制平面建议仍然放在 `t9-ct1`：

- `etcd`：`10.10.9.1:2379`
- `apiserver`：`10.10.9.1:18100`

这样所有 shard 节点都只需要把：

- `etcd_host` 指向 `10.10.9.1`

同时，非 bootstrap 节点的：

- `default_join_host`

也可以统一先指向拥有 bootstrap 节点的目标容器。

## 在 mac 上如何模拟“5 个容器 + 固定 IP”

做法是：

1. 创建一个 Docker 自定义网络
2. 子网设成 `10.10.9.0/24`
3. 建 5 个容器
4. 分别分配固定 IP：
   - `t9-ct1 -> 10.10.9.1`
   - `t9-ct2 -> 10.10.9.2`
   - `t9-ct3 -> 10.10.9.3`
   - `t9-ct4 -> 10.10.9.4`
   - `t9-ct5 -> 10.10.9.5`

只要这些容器都在同一个 Docker 网络里，它们就可以互相通过这些地址访问。

## 能不能像验收时那样用 SSH 连 5 个容器

可以，但要区分两种方案。

### 方案 A：更省事，使用 `docker exec`

这是最稳、最快、最适合先排错的方案。

做法是：

- 不在容器里装 `sshd`
- 直接从宿主机开 5 个终端
- 每个终端分别执行：
  - `docker exec -it t9-ct1 sh`
  - `docker exec -it t9-ct2 sh`
  - `docker exec -it t9-ct3 sh`
  - `docker exec -it t9-ct4 sh`
  - `docker exec -it t9-ct5 sh`

优点：

- 不需要改镜像
- 不需要维护 SSH 用户、密钥和端口映射
- 更适合快速调试

缺点：

- 登录方式不像验收环境
- 不能练习真正的 `ssh` 命令

### 方案 B：更像验收环境，在容器里跑 `sshd`

这是更接近验收流程的方案。

做法是：

- 基于当前镜像额外做一层包装
- 在容器里安装并启动 `openssh-server`
- 给每个容器映射不同的宿主机端口，例如：
  - `t9-ct1 -> localhost:2201`
  - `t9-ct2 -> localhost:2202`
  - `t9-ct3 -> localhost:2203`
  - `t9-ct4 -> localhost:2204`
  - `t9-ct5 -> localhost:2205`

然后你可以在 mac 上开 5 个终端，分别执行：

```bash
ssh -p 2201 app@127.0.0.1
ssh -p 2202 app@127.0.0.1
ssh -p 2203 app@127.0.0.1
ssh -p 2204 app@127.0.0.1
ssh -p 2205 app@127.0.0.1
```

优点：

- 操作习惯更接近验收时“登录容器后部署”
- 可以提前练习远程登录、日志查看和手工启动流程

缺点：

- 需要自定义镜像
- 需要维护 `sshd`
- 仍然不是 100% 复刻“同一个跳板 IP + 同一个端口 + 不同用户名路由到不同容器”的学校环境

### 推荐结论

建议先做：

- 方案 A：`docker exec`

等流程跑通以后，如果你确实需要“练习 SSH 操作感”，再加：

- 方案 B：`sshd`

## 能不能用 5 个终端监控，再用 1 个终端控制

完全可以，这其实是这套 mock 最适合的使用方式。

推荐终端分工如下：

- 终端 1：连接 `t9-ct1`，作为控制面终端
- 终端 2：连接 `t9-ct2`，监控 shard 进程
- 终端 3：连接 `t9-ct3`，监控 shard 进程
- 终端 4：连接 `t9-ct4`，监控 shard 进程
- 终端 5：连接 `t9-ct5`，监控 shard 进程
- 终端 6：宿主机本地终端，用于发 `ssh`、`docker exec`、`curl`、`ddb-cli`

### 控制面终端做什么

控制面终端建议专门负责：

- 启动 `etcd`
- 启动 `apiserver`
- 执行：
  - `./bin/ddb-cli --node-url=http://10.10.9.1:18100 interact`
  - `control groups`
  - `control shards`
  - `control move-shard`

也就是说，它就是你正式演示时的“统一入口终端”。

### 其他容器终端做什么

其他 4 个数据容器终端可以分别用来：

- 看日志
- 检查端口
- 手工启动或停止该容器内的 shard 进程
- 模拟某个容器故障
- 观察某个 group 是否失去多数派

## 能否模拟 inspect 场景

可以，而且这套 5 容器 mock 非常适合提前演练 `inspect`。

因为 `inspect` 的核心不是“容器数够不够”，而是：

- 9 个 shard 节点真实存在
- 它们被分散在多个容器里
- 你可以直连每个节点的 HTTP 地址做本地检查

只要容器内和容器间网络通，你就能提前验证：

- 插入一条记录后，到底是哪 3 个副本持有这条数据
- 剩下 6 个副本为什么没有

这正好对应课程演示里最有说服力的一段。

## 需要提前接受的几个限制

这套 mock 很有价值，但也有几个现实限制：

### 1. 不能完全复刻学校的跳板 SSH 入口

学校环境是：

- 同一个外部地址
- 同一个端口
- 通过用户名进入不同容器

本地更现实的做法通常是：

- 不同本地端口映射到不同容器
- 或直接 `docker exec`

### 2. mac 宿主机对容器内网 IP 的访问体验和 Linux 不完全一样

容器之间用 `10.10.9.x` 互通没有问题，但：

- 宿主机是否能直接访问这些 IP
- 路由和端口暴露方式

和 Linux 原生 Docker 不完全一致。

### 3. 当前仓库没有现成的 Linux 多进程容器脚本

现成脚本主要是：

- `scripts/ddb-mac-control.sh`
- `scripts/ddb-mac.sh`
- `scripts/ddb-win-control.ps1`
- `scripts/ddb-win.ps1`

它们不是为 Linux 容器环境直接设计的。

所以如果要做这套 mock，后续还需要：

- 一套 Linux 容器版配置
- 一套 Linux 多进程启动脚本
- 可选的 `sshd` 容器包装

## 推荐推进顺序

建议按下面顺序推进：

1. 先在 mac 上起 5 个固定 IP 容器
2. 先用 `docker exec` 进入容器，而不是一开始就做 SSH
3. 先把控制平面 + 9 个 shard 进程跑通
4. 验证 `interact`、`inspect`、`move-shard`、故障演示
5. 如果都稳定，再补 `sshd`，练习“更像验收”的操作方式

这是最稳的路线。

## 最终建议

如果你的目标是：

- 尽量早发现验收部署问题
- 保持当前系统设计不大改
- 又能提前练手 5 节点环境

那么最推荐的结论是：

- 保持现在的 `3 group × 3 replica`
- 在 mac 上 mock 出 `t9-ct1` 到 `t9-ct5`
- 容器内网 IP 固定成 `10.10.9.1` 到 `10.10.9.5`
- 一个容器跑多个 shard 进程
- 第一阶段用 `docker exec`
- 第二阶段如有需要再补 `ssh`

## 下一步可以继续做什么

如果这份方案确认可行，下一步建议直接落地以下内容：

1. 一份 5 容器 Docker Compose 文件
2. 一套 Linux 容器 mock 配置文件
3. 一套 Linux 容器多进程启动脚本
4. 一份本地演练 runbook
5. 可选的 `sshd` 容器版镜像和登录方式
